# ADR 0003：把离线缓存钩在传输层，而不是每个 Repository

- 状态：已采纳（2026-11-17）
- 相关：ADR 0002（进度 outbox）、`docs/offline-cache.md`

## 背景

进度在阶段 B 已经"离线性"了（先落盘、断网补交），但**内容没有**：断网冷启动书架是错误页，
一本书看过的页也调不出来。用户对"离线"的期待很朴素——**看过的东西应该还能看**。

候选做法有三个：

1. 每个 Repository 方法各写一遍"失败读缓存"。书架、系列、书、页列表、页图、封面……
   六七个方法，漏一个就是半残；新加端点时也没人提醒。
2. 在 dio 上加一个缓存拦截器。能覆盖所有请求，但拦截器拿到的是 `Response`，
   要自己区分 JSON/字节、自己解析错误；而 `komga_api` 的错误折叠逻辑在 `_getJson/_getBytes` 里，
   两套错误判断会漂移。
3. 在 `KomgaSession` 的 GET 出口/入口做（**采纳**）。

## 决策

### 1. 缓存接口在 `komga_api`，实现放在 app

`HttpCache`（`packages/komga_api/lib/src/http_cache.dart`）只有四个方法：`read`/`write`/
`reportOnline`/`reportOffline`。具体存储是 Drift（app 层），因为 `komga_api` 必须保持纯 Dart
（分层门禁会拦 drift）。单测里用内存假实现就能覆盖"命中/未命中/不该回退"。

### 2. 只在 GET 上缓存，且只对"网络类失败 + 5xx"回退

- 404 说明资源真被删了，拿缓存会让用户看到已经不存在的东西；
- 401/403 是登录态问题，不是离网——这时该弹"重新登录"，不是"你在看缓存"；
- 406/协议错误说明服务端就在那儿但答非所问，回退会把真正的配置问题藏起来。

PATCH（进度）不缓存：它有 outbox 自己的重试语义，两套重试叠在一起只会更难查。

### 3. 缓存与进度分两个 SQLite 文件

`komga_native.sqlite`（进度）与 `komga_cache.sqlite`（内容）分开。

进度是**不可再生**的用户数据（丢了就是丢了），缓存随时可以清空重建。
放同一个库会让"清缓存"存在误伤用户数据的风险，也会让备份/迁移策略互相牵制。
代价是多一个数据库连接——SQLite 完全承受得起。

### 4. JSON 不参与字节预算淘汰

页图/封面是大头（几百 KB～几 MB），JSON 很小但**是"书架和书能不能打开"的前提**。
所以：

- 被动浏览图片（`pinned = false`）：总字节预算 256 MB，LRU 淘汰；已整本下载页图（`pinned = true`）独立受保护，永不被被动浏览挤掉；
- JSON：按条数（每服务器 400 条）裁剪最久未用的，不会因为"图片太多"被挤掉。

### 5. LRU 用单调序号，不用时间戳

Drift 默认把 `DateTime` 存成 **秒**。第一版用 `lastUsedAt` 排序，测试当场抓到：
同一秒内的多次写入全部并列，淘汰变成"随机删"。改成 `lastUsedSeq`（整数，单调递增，
进程重启后从 `MAX(seq)` 续上），既没有精度问题，也没有时钟回拨问题。

### 6. 刚写入的那条不能被自己挤掉

一张 8 MB 的长图单独就超过预算。淘汰时必须保护刚写入的 URL，否则"越大的图越存不下来"，
用户等完下载发现离线还是打不开。允许暂时超预算，下一次写入再还。

## 后果

**得到**：

- 断网冷启动能看到上次的书架、封面、读过的页；不用为每个 Repository 重复写回退逻辑；
- 离线状态是**真实观测**（传输层报告），不是猜的网络类型；
- 清缓存与清进度互不影响。

**放弃/边界**：

- 缓存键是完整 URL：`?convert=jpeg` 与原图是两份；换 `Accept` 头也可能产生不同响应；
- 没访问过的页离线仍然打不开（整本下载是阶段 D 的事）；
- 缓存不区分账号：同一服务器换账号会共用同一份内容缓存（内容本身与账号无关，
  但"这个账号能不能看"这件事离线时无法校验）；
- 缓存不加密：服务端内容落在应用私有目录，与"下载到本地"是同一类隐私暴露面。
